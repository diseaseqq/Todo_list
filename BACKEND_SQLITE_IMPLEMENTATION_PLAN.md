# План разработки backend на PHP и SQLite

## Назначение документа

Этот документ задаёт обязательный порядок перехода приложения списка задач с `localStorage` на backend на PHP и SQLite. Агент, который выполняет разработку, должен сначала прочитать этот план, сверить его с текущим репозиторием, выполнять этапы по порядку и отмечать критерии готовности. Не пропускать этапы и не менять архитектурные решения молча. Если ответ на вопрос из раздела «Решения, требующие уточнения» влияет на текущий этап, остановиться до реализации этого этапа и запросить решение.

План охватывает серверное хранение, API, backend-логику аккаунтов, простую форму входа, миграции схемы и переключение существующего интерфейса задач. Перенос старых пользовательских данных, формы регистрации и управления аккаунтом, а также интерфейс администратора не входят в объём работ. Облачную синхронизацию и иные крупные функции не добавлять без отдельного согласования.

## Исходное состояние проекта

Сейчас это статическое приложение на HTML, CSS и JavaScript без сборщика и PHP-кода. Данные хранятся в `localStorage`. Основные сущности и сценарии:

- задачи с названием, описанием, приоритетом, сроком и категорией;
- выполнение и редактирование задач;
- подзадачи с собственным статусом;
- повторения: ежедневно, еженедельно, ежемесячно и пользовательский интервал в днях;
- категории, включая стандартные и пользовательские;
- архивирование, восстановление, восстановление всех задач и окончательное удаление;
- поиск по названию и описанию, фильтр и сортировка;
- статистика задач и настройки темы;
- JSON-резервные копии задач, архива и категорий.

Перед изменениями агент обязан повторно проверить актуальные исходники: этот список может устареть. UI-поведение не менять, если это не требуется для API, миграции или согласованного решения.

### Результаты аудита текущего приложения

Аудит исходников `js/script.js`, `index.html` и `README.md` выполнен для подпункта 1 этапа 0.

- Состояние задач, архива и категорий хранится в ключах `todo_tasks`, `todo_archived` и `todo_categories` в `localStorage`; тема хранится отдельно в `todo_theme`. При загрузке массивы нормализуются и сразу сохраняются обратно.
- Задача содержит строковый ID, название, необязательные описание/срок/категорию, приоритет, признак выполнения, подзадачи, правило повтора и числовой `createdAt` в миллисекундах. Отдельного `completedAt` нет. Название после trim проверяется как 3–150 символов; описание ограничено 500; приоритеты `low`/`medium`/`high`; срок проверяется как реальная календарная дата `YYYY-MM-DD`. Подзадачи ограничены названием в 150 символов, отдельного ограничения их количества не найдено.
- Категории — строки. Есть шесть встроенных значений и пользовательские категории до 50 символов. Дубликаты сравниваются через `toLocaleLowerCase('ru-RU')`. Удаление категории снимает её со всех активных и архивных задач.
- Удаление задачи из основного списка означает перемещение в архив с `deletedAt`; предусмотрены восстановление одной/всех задач и окончательное удаление одной/всех архивных задач с подтверждением. Архивная задача хранит прежние поля, в том числе признак выполнения и повтор.
- JSON backup имеет `format: "todo-list-backup"`, `version: 1`, `exportedAt`, `tasks`, `archivedTasks`, `categories`. Экспорт локальный. Импорт ограничен 10 МБ, проверяет только маркер/наличие массивов верхнего уровня, затем нормализует и заменяет все три массива. Три записи в `localStorage` выполняются отдельно, поэтому при ошибке хранения импорт может сохраниться частично. Этот старый формат не переносится в новую серверную базу согласно принятому решению.
- Поддерживаются повторы `daily`, `weekly`, `monthly` и `custom` (1–365 дней). Следующая задача создаётся сразу при переводе исходной из невыполненной во выполненную; копируются заголовок, описание, приоритет, категория и правило, но подзадачи не копируются. Расписание ориентируется на исходный срок и пропускает даты до сегодняшнего дня. Будущие экземпляры заранее не создаются, серийного ID или истории версий правил в текущем приложении нет.
- Месячный алгоритм ограничивает число последним днём целевого месяца. Поэтому последовательность с 31 января идёт на 28 февраля, а затем обычно на 28 марта; выбор правила для этой ситуации остаётся открытым продуктовым решением.

Эти сведения описывают текущее поведение для проектирования API и проверки сохранения согласованных сценариев; они не отменяют принятый отказ от импорта локальных данных.

## Целевой результат

1. PHP предоставляет JSON API для операций приложения, включая backend-сценарии аккаунтов.
2. SQLite хранит задачи и связанные данные на сервере.
3. Backend поддерживает создание аккаунта, вход, выход, текущую сессию и изоляцию данных по владельцу.
4. Приложение предоставляет простую форму входа, но не формы регистрации или управления аккаунтом.
5. Существующий интерфейс задач получает и изменяет данные через API, а не сохраняет рабочее состояние напрямую в `localStorage`.
6. Новая база начинает работу пустой; импорт старых данных из `localStorage` и legacy JSON не выполняется.
7. Ошибки, повторные запросы, ограничения и удаление связанных записей обрабатываются предсказуемо.
8. Установка, миграции схемы, резервное копирование и восстановление описаны в README или отдельной эксплуатационной инструкции.

## Обязательные архитектурные правила

- Использовать PHP PDO с драйвером PDO_SQLITE. Проверить доступность расширения на целевом окружении до начала интеграции.
- Все значения пользователя передавать в SQL через подготовленные выражения. Не собирать SQL подстановкой пользовательских строк.
- Включать внешние ключи для каждого соединения с SQLite. SQLite не следует считать включившей их автоматически. См. [SQLite Foreign Key Support](https://www.sqlite.org/foreignkeys.html).
- Все многошаговые изменения выполнять в транзакции. В частности, завершение повторяющейся задачи и создание следующего экземпляра должны быть атомарными. См. [PDO transactions](https://www.php.net/manual/en/pdo.transactions.php).
- Хранить файл базы вне публичного каталога веб-сервера и не добавлять его, журналы SQLite и секреты в Git.
- Хранить даты срока как `YYYY-MM-DD`; временные метки создания, изменения и выполнения — в UTC в одном согласованном ISO-8601 формате.
- Ограничивать значения схемой: приоритет, частота повтора, булевы поля, обязательный заголовок, длины строк и интервалы.
- Использовать миграции схемы с номером версии; не рассчитывать на ручное создание таблиц или редактирование боевой БД.
- Не хранить вычисляемый прогресс подзадач, если его можно надёжно посчитать из таблицы подзадач.
- Не считать SQLite подходящей для нескольких серверов, которые одновременно пишут в общий сетевой файл. При одном сервере оценить WAL и таймаут блокировки с учётом хостинга. WAL улучшает параллельность чтения и записи, но не отменяет ограничения SQLite на конкурентные записи. См. [SQLite Write-Ahead Logging](https://www.sqlite.org/wal.html).
- Ответ API не должен раскрывать SQL, файловые пути, трассировки или секреты. Полные детали ошибок писать только в серверный журнал.

## Предварительная модель данных

Окончательный DDL не создавать, пока не приняты решения из раздела «Решения, требующие уточнения». Имена ниже концептуальные.

### `users`

- `id` — строковый UUID, первичный ключ;
- `email` — нормализованный адрес, уникальный;
- `password_hash` — только хеш, рассчитанный серверным API;
- `role` — `admin` или `user`, с проверкой допустимых значений;
- `status` — состояние аккаунта, ограниченное разрешёнными значениями;
- `created_at`, `updated_at`.

Для email хранить нормализованное значение и обеспечить уникальность. Политику нормализации email определить до миграции. Пароль никогда не хранить и не возвращать в открытом виде. Все пользовательские данные должны иметь владельца.

### `categories`

- `id` — строковый UUID, первичный ключ;
- `owner_id` — обязательный внешний ключ на `users`;
- `name` — отображаемое название;
- `normalized_name` — нормализованное имя для уникальности без учёта регистра, включая кириллицу;
- `is_system` — признак стандартной категории;
- `created_at`, `updated_at`.

Уникальность категории задавать на область владельца и `normalized_name`. Не полагаться на SQLite `NOCASE` для корректного Unicode case-folding: нормализованное значение формировать на стороне PHP с Unicode-функциями и проверить наличие `mbstring` либо выбрать однозначную замену.

### `task_series`

Хранит идентичность серии и её текущее состояние:

- `id`, обязательный `owner_id` — FK на `users`;
- `is_active`, `created_at`, `updated_at`.

### `task_series_rules`

Хранит версии шаблона серии, чтобы изменения применялись только вперёд и история правила не терялась:

- `id` — строковый UUID, первичный ключ;
- `series_id` — обязательный FK на `task_series`;
- `version` — возрастающий номер версии, уникальный в рамках серии;
- поля шаблона будущей задачи: `title`, `description`, `priority`, `category_id`;
- `recurrence_type`: `daily`, `weekly`, `monthly` или `custom`;
- `interval_days` для `custom`, ограниченный диапазоном 1–365; для остальных типов использовать фиксированное правило;
- исходную дату/календарный якорь серии — как минимум исходное число месяца для `monthly`, чтобы правило «последний день короткого месяца» не сдвигало последующие месяцы;
- `effective_from`, `created_at`.

Поля начала, окончания или часового пояса добавлять только при подтверждённом требовании планировать повтор по времени суток. Текущий интерфейс оперирует датой без времени.

### `tasks`

- `id` — строковый UUID, первичный ключ;
- `owner_id` — обязательный внешний ключ на `users`;
- `series_id` — nullable FK на `task_series`;
- `series_rule_id` — nullable FK на версию правила, по которой создан этот экземпляр;
- `category_id` — nullable FK на `categories`;
- `title` — обязательная строка, 3–150 символов после trim;
- `description` — nullable, максимум 500 символов;
- `priority` — `low`, `medium` или `high`;
- `due_date` — nullable дата `YYYY-MM-DD`;
- `is_completed` — 0/1;
- `completed_at` — nullable UTC timestamp;
- `archived_at` — nullable UTC timestamp; не создавать отдельную таблицу архива;
- `version` — монотонно возрастающий номер для оптимистической блокировки конкурентных изменений;
- `created_at`, `updated_at`.

Каждый экземпляр серии хранится отдельной строкой задачи со снимком её полей и ссылкой на версию правила. При изменении повторяющейся задачи новая версия шаблона применяется только к будущим незавершённым экземплярам; выполненные экземпляры сохраняются как история и массово не переписываются. Генерация следующих экземпляров использует последнюю действующую версию. Выполненность и архив — независимые состояния. Окончательное удаление задачи удаляет её подзадачи, но не должно удалять историю правила, на которую ссылаются другие экземпляры.

### `subtasks`

- `id` — строковый UUID, первичный ключ;
- `task_id` — обязательный FK на `tasks` с каскадным удалением;
- `title` — обязательный текст;
- `is_completed` — 0/1;
- `sort_order` — порядок отображения;
- `created_at`, `updated_at`.

### Индексы

После определения запросов добавить индексы для срока выполнения, категории, владельца (если применимо), состояния архива и выполнения, а также `subtasks.task_id` и `tasks.series_id`. Не добавлять индексы без сценария чтения. Проверить планы основных запросов на тестовом наборе данных.

## Решения, требующие уточнения

До соответствующего этапа агент обязан получить ответы или явно записать утверждённые предположения:

1. **Проверка доступности IP для TLS:** при развёртывании подтвердить, что `132.243.19.228` — постоянный публичный адрес и сервер доступен для ACME-проверки по HTTP-01 или TLS-ALPN-01.

### Принятые решения по вопросам

- **Сервер и база:** целевой сервер — постоянный публичный IP `132.243.19.228`; приложение должно открываться напрямую по этому IP без доменного имени. Для развёртывания принять каталоги: код приложения `/var/www/todo-list`, публичный каталог Nginx `/var/www/todo-list/public`, база `/var/lib/todolist/app.sqlite`, резервные копии `/var/backups/todolist`. Код и public: `root:root`, каталоги `0755`, файлы `0644`; каталог базы: `www-data:www-data`, `0750`, файл БД `0640`; каталог резервных копий: `root:root`, `0700`, задача backup выполняется с root-доступом или эквивалентно ограниченным доступом. Эти права обеспечить при развёртывании, не предоставлять PHP-FPM запись к коду или backup-каталогу. База и копии находятся на том же сервере, но вне публичного web-root.
- **Веб-сервер и HTTPS:** выбран Nginx; доменного имени нет, HTTPS пока не настроен. Настроить виртуальный хост Nginx для IP `132.243.19.228`; после настройки TLS основной адрес приложения — `https://132.243.19.228`, HTTP перенаправляется на HTTPS. Использовать TLS-сертификат Let's Encrypt для публичного IP-адреса с профилем короткоживущих сертификатов и автоматическим обновлением. Такие сертификаты действуют около 160 часов, поэтому автоматическое обновление должно быть настроено и проверено до production. В APT Ubuntu 24.04 найден Certbot 2.9.0, который ниже требуемого для IP-сертификатов; использовать поддерживаемую версию Certbot 5.4+ (официальный канал установки) в режиме `webroot`, а конфигурацию/перезагрузку Nginx подготовить отдельно, поскольку Certbot пока не выполняет автоматическую установку IP-сертификата в Nginx. Для выдачи потребуется пройти ACME-проверку контроля IP.
- **Месячные повторы:** если целевого числа в месяце нет, использовать последний день этого месяца. Расчёт повторов должен сохранять исходное календарное число серии, чтобы после короткого месяца дата возвращалась к исходному числу (например, 31 января → 28 февраля → 31 марта), а не сдвигалась навсегда.
- **Категории:** пользователь может удалять и переименовывать категории, включая стандартные. Удаление категории снимает её назначение с задач, не удаляя сами задачи. Добавить переименование в API и интерфейс при реализации соответствующего этапа.
- **Аккаунт и email:** адрес email обрезается по краям и приводится к нижнему регистру перед проверкой уникальности и сохранением; для Unicode case-folding категорий использовать `mb_convert_case(..., MB_CASE_FOLD, 'UTF-8')`. Состояния аккаунта на первом этапе — `active` и `disabled`. Стандартные категории приложения (`Работа`, `Личное`, `Учёба`, `Покупки`, `Спорт`, `Другое`) создаются отдельно для каждого аккаунта, включая первого администратора; отметка стандартной категории не запрещает её переименование или удаление. Пароль первого администратора вводится интерактивно, минимум 12 символов и не более 72 байт для совместимости с `PASSWORD_DEFAULT`.
- **Одновременное редактирование:** защита от потери более свежих изменений нужна. Применить оптимистическую блокировку через поле версии или `updated_at`: изменение принимается только при совпадении версии клиента с текущей серверной; при конфликте API возвращает отдельный статус (например, HTTP 409), клиент сообщает о конфликте и предлагает загрузить актуальную запись. Автоматически сливать изменения не требуется.

### Принятое решение по размещению

Приложение будет размещено на удалённом сервере Ubuntu 24.04. Выбрать PHP 8.3 из репозиториев Ubuntu 24.04: это штатная ветка для этой LTS-системы, для неё доступны CLI, FPM и модуль SQLite без стороннего PPA. Установить согласованные версии пакетов `php8.3-cli`, `php8.3-sqlite3`, `php8.3-mbstring` (если выбрана нормализация Unicode через mbstring) и `php8.3-fpm`, если этого требует выбранный веб-сервер. Обновления безопасности получать через APT. Ветка PHP 8.3 поддерживается upstream исправлениями безопасности до 31 декабря 2027 года; до этой даты запланировать переход на более новую поддерживаемую ветку, доступную в Ubuntu или согласованном источнике пакетов. Проверить `apt policy` на сервере до установки.

Работы по установке и настройке сервера относятся к отдельному этапу развёртывания. До интеграции проверить фактически загруженные PHP-модули и доступность SQLite через PDO. Файл базы и резервные копии хранить вне публичного web-root с ограниченными правами.

### Принятое решение по резервному копированию

Выполнять согласованное резервное копирование базы ежедневно в 03:00 UTC. Хранить последние 7 ежедневных и 4 еженедельных копии; еженедельную копию формировать из снимка за воскресенье. Копировать SQLite через Backup API или другой согласованный безопасный механизм, поддерживающий WAL. Проверять восстановление не реже одного раза в квартал и после изменения процедуры резервирования. Ротация касается только резервных копий; автоматическая очистка данных приложения запрещена.

### Принятое решение по аккаунтам

Аккаунты и разделение данных пользователей обязательны. Backend должен реализовать регистрацию через API, вход, выход, получение текущего аккаунта и проверку владельца для каждой операции с задачами, категориями и сериями. В интерфейсе реализовать простую форму входа по email и паролю; формы регистрации и управления аккаунтом не создавать. Использовать серверные сессии с cookie-флагами `HttpOnly`, `Secure` в HTTPS и `SameSite`; для изменяющих запросов предусмотреть CSRF-защиту. Создание и проверку паролей выполнять только на сервере безопасными средствами PHP; в БД хранить только хеш.

До включения публичной регистрации и защищённых бизнес-маршрутов необходимо подготовить схему аккаунтов и безопасно создать первый аккаунт с ролью `admin`. Первый администратор создаётся оператором через CLI-команду начальной настройки после применения миграций. Команда должна запросить email и пароль интерактивно, не принимать пароль в аргументах командной строки, сохранить только хеш и завершаться ошибкой, если начальный администратор уже создан. Не добавлять стандартные email/пароль, не создавать администратора автоматически при каждом запуске и не помещать секреты в код, Git или журналы.

Backend должен иметь регистрацию обычного `user`, вход, выход и endpoint текущего аккаунта. Форма входа должна показываться неавторизованному пользователю, отправлять credentials только по HTTPS в production и не сохранять пароль в `localStorage`. После успешного входа клиент получает только безопасные сведения текущего аккаунта и загружает рабочий интерфейс задач. Выход завершает серверную сессию. Ошибка входа должна быть понятной, но не раскрывать, существует ли указанный email. Восстановление пароля, подтверждение email, регистрационную форму и интерфейс администратора не добавлять без отдельного требования.

На первых этапах роль `admin` не даёт специальных полномочий. Первый администратор использует приложение только для работы со своими задачами, как обычный пользователь. Не создавать admin-only API, не разрешать просмотр или изменение чужих данных и не добавлять управление аккаунтами. Роль оставить в модели как зарезервированную для будущего расширения; расширение прав потребует отдельного требования и проверки авторизации.

Не добавлять обход авторизации, который принимает `user_id` от клиента или автоматически выбирает владельца в production. Backend-сценарии проверять через API-клиент/автотесты с обычной сессией. Для локальной разработки допускается только документированный тестовый способ входа, который полностью отключён вне development/test окружений.

### Принятое решение по переносу старых данных

Перенос существующих данных из `localStorage` или старого JSON-файла в новую серверную базу не требуется. Новая база запускается пустой. Не добавлять разовый импортёр старого клиентского хранилища в рамках этой задачи. Это решение не отменяет резервное копирование и восстановление уже созданной серверной базы; формат этих операционных копий описать отдельно.

### Принятое решение по автоматической очистке

Автоматическая очистка данных не нужна. Не добавлять фоновые задания, политики срока хранения или автоматическое удаление задач, архива, аккаунтов и истории повторений. Удаление данных выполняется только явно инициированными действиями приложения, с проверкой владельца и предусмотренной подтверждающей логикой. Плановое резервное копирование и выбранный отдельно срок хранения резервных копий являются эксплуатационными процедурами, а не очисткой данных приложения.

### Принятое решение по повторяющимся задачам

Изменения шаблона серии применяются только к будущим экземплярам. Уже выполненные экземпляры не изменяются и сохраняются для истории. Версия правила, по которой создан экземпляр, должна оставаться доступной через `task_series_rules`. Остаётся определить поведение месячного повтора для отсутствующего числа месяца.

Если ответ не получен, агент не должен молча придумывать продуктовую логику. Он может продолжать независимые этапы, но должен оставить зависимый этап заблокированным и описать, какое решение требуется.

- получить статистику задач и архива.

**Критерии выхода:** есть проверяемая процедура резервного копирования и восстановления; при блокировке БД пользователь получает контролируемую ошибку, а не необработанный стек.
